# Review of the two pharma repositories

Reviewed `mcgrath-bpt/pharma-commercial-lab` at `912713205f7d738dff330db5d00c04121b099af1` and `mcgrath-bpt/opharma` at `26b04c45f8ca8d5a61758beb6991872a572ed75d`.

Scope: first-party Python, SQL, tests, contracts and relevant documentation. The vendored analytics plugin under `agentic/skills` was excluded from the application review. `opharma` contains a README, gitignore and draft SQL in `scratch/notes.md`, with no runnable application or test suite.

## Findings

1. **[P1] Ambiguous source customer keys can resolve to the wrong person.** [reference.py:48–52](https://github.com/mcgrath-bpt/pharma-commercial-lab/blob/912713205f7d738dff330db5d00c04121b099af1/src/reference.py#L48-L52) checks uniqueness per token, but overwrites the mapping if the same CRM/customer or Salesforce/contact key has two different tokens, each pointing to a different active provider. Reversing those two records changed the customer assigned to the same engagement in a local reproduction. This can apply another customer's consent and corrupt S1/S2/S5. Group candidates by source key and require exactly one distinct provider before resolving it. [The SQL maps](https://github.com/mcgrath-bpt/pharma-commercial-lab/blob/912713205f7d738dff330db5d00c04121b099af1/sql/02_reference_gold.sql#L14-L21) also lack source-key uniqueness and would retain both matches rather than quarantine the ambiguity; that SQL consequence was established by inspection, not Snowflake execution.

2. **[P2] Malformed activity fields escape record-level quarantine.** [reference.py:63–74](https://github.com/mcgrath-bpt/pharma-commercial-lab/blob/912713205f7d738dff330db5d00c04121b099af1/src/reference.py#L63-L74) parses `source_version` before its exception handler. A blank or `oops` version aborts calculation with `ValueError`, rather than producing `S04/INVALID_TYPE` and preserving other valid records. A timestamp without a timezone parses successfully but subsequently aborts with `TypeError` when compared with the UTC cutoff. Validate the integer version and timezone semantics within the record classification path; cover both activity headers and product-detail versions. The hand-built SQL already classifies invalid activity versions as `INVALID_TYPE`, so the Python behavior also differs from that baseline.

3. **[P2] Reconciliation accepts malformed output rows.** [validate.py:43–45](https://github.com/mcgrath-bpt/pharma-commercial-lab/blob/912713205f7d738dff330db5d00c04121b099af1/src/validate.py#L43-L45) checks the header but ignores surplus row fields stored by `DictReader` under the `None` key. Adding `,unexpected` to one S4 result row still returned `passed=True`. This undermines the exact output acceptance gate. Validate row widths and reject extra or missing cells before comparing multisets.

4. **[P2] Consent conflict detection depends on input order.** [reference.py:91–94](https://github.com/mcgrath-bpt/pharma-commercial-lab/blob/912713205f7d738dff330db5d00c04121b099af1/src/reference.py#L91-L94) compares each event only with the latest event retained so far. A conflicting pair of older events fails when processed before a newer event, but is silently accepted when the newer event appears first. Reproduced using `CONSENT-000003`, a conflicting status at its same rank, and `WITHDRAW-3`. Track all `(provider, channel, effective_at, sequence_no)` ranks separately from selecting the latest status. The SQL checks conflicts across all candidate ranks, so the Python reference can also disagree with SQL.

5. **[P2] Identical product redelivery is treated as hierarchy ambiguity.** [reference.py:58–59](https://github.com/mcgrath-bpt/pharma-commercial-lab/blob/912713205f7d738dff330db5d00c04121b099af1/src/reference.py#L58-L59) compares complete row dictionaries, including `_batch_id`, `_available_at` and `_mode`. Resending an unchanged current product in b002 therefore raises `AMBIGUOUS_PRODUCT_HIERARCHY`. Compare the business payload independently of delivery metadata and retain failure for genuinely conflicting current hierarchies. The SQL projection already excludes that metadata when deduplicating current products.

6. **[P2] The draft representative view merges distinct reps with the same name.** [opharma scratch/notes.md:83–99](https://github.com/mcgrath-bpt/opharma/blob/26b04c45f8ca8d5a61758beb6991872a572ed75d/scratch/notes.md#L83-L99) projects only `full_name` and `territory_code` as grouping keys. `GROUP BY ALL` therefore merges two distinct rep IDs sharing a name and territory. A reproduction with two Alex Smith reps, each visiting the same HCP once, returned one row with two visits and one reached HCP. Include `rep_id` in the projection/grouping. The reproduction used SQLite with the equivalent explicit grouping, because DuckDB was not available.

## Validation and limits

Executed `python3 src/run_local.py --data /tmp/pharma-review-fixture`: all seven result tables reconciled at both b001 and b002; 5,346 public delivery rows passed validation. The suite reported 16 tests: 15 passed and one workbook test skipped. A fresh deterministic fixture was generated from the reviewed configuration.

The GitHub connector supplied text files after direct cloning failed because the execution environment's proxy was unreachable. The connector rejects binary workbook retrieval, so XLSX roundtrip behavior could not be verified here. AWS/S3 and Snowflake execution were not performed; cloud-related conclusions above are explicitly static. Repository source code was not patched, and no changes were published to GitHub.
